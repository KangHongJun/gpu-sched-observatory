# GPU Scheduling Observatory MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 4주 안에 GPU 공유 경합(Context 전환, 커널 중첩, MPS 효과)을 터미널에서 보여주는 `gso` CLI/TUI의 MVP를 만들고 공개 준비까지 마친다.

**Architecture:** NVML·DCGM을 폴링하는 Metric Provider와 nsys on-demand 캡처를 읽는 Trace Provider가 공통 `Record`를 bounded ring buffer에 넣고, 순수 함수로 된 분석 계층이 파생 지표를 계산해 TUI·JSONL/CSV·벤치마크 비교가 소비한다. 1주차는 코드보다 검증이 먼저이며, 검증 결과(게이트 G1~G6)가 3~4주차 범위를 결정한다.

**Tech Stack:** Python 3.10+, uv, nvidia-ml-py, Textual, sqlite3(표준 라이브러리), argparse, pytest, ruff. 벤치마크 워크로드는 PyTorch(선택 의존성). 외부 도구: `dcgmi`, `nsys`, `nvidia-cuda-mps-control`.

**Spec:** [docs/specs/2026-11-25-gpu-scheduling-observatory.md](../specs/2026-11-25-gpu-scheduling-observatory.md)

## 스택 결정: MVP는 Python

spec은 C++17/20 + FTXUI를 추천하면서 "빠른 검증은 Python으로 시작해도 된다"고 했다. MVP 전체를 Python으로 간다.

- 이 장비에 `cmake`, `nvcc`, CUDA toolkit이 없고 sudo는 비밀번호가 필요하다. C++ 빌드 환경을 갖추는 데 1주차를 쓰게 된다.
- MVP의 수집 경로는 1초(지원 시 100ms) 폴링과 nsys SQLite 파싱이다. Python으로 충분하다.
- C++가 실제로 필요한 것은 CUPTI 실시간 collector인데, spec이 이를 MVP 이후로 분류했다.

## Global Constraints

- 지원 대상: Linux x86_64, RTX A5000, NVIDIA CUDA 환경. Jetson·멀티 GPU·Prometheus는 MVP 범위 밖.
- 미지원 지표는 0이 아니라 `N/A`로 표시한다. 내부 표현은 `value=None`, `quality=UNSUPPORTED`.
- 측정값/추정값/미지원/유실을 `quality`로 구분한다. 시간 상관관계로 PID에 귀속한 값은 `ESTIMATED`.
- 운영 중인 MPS 서버나 생산 워크로드를 자동 변경하지 않는다. 도구가 직접 띄운 MPS 데몬만 종료한다.
- `dcgmi profile --pause` / `--resume`은 host engine 전체에 영향을 주므로 실행하지 않는다.
- nsys 캡처를 "실시간 스트리밍"이라고 표현하지 않는다. UI·문서 문구는 "on-demand capture".
- Context 비활성 시간을 전환 오버헤드로 취급하지 않는다. 커널 구간 중첩을 SM 단위 동시 실행량이라고 표현하지 않는다.
- 모든 실험·테스트는 GPU 1에서만 한다. 코드의 GPU 선택 기본값은 없고 `--gpu`가 필수다.
- 시스템 전역 캡처(`--gpuctxsw`)에는 다른 사용자의 PID가 들어간다. 원본은 `docs/verification/raw/`(gitignore)에만 두고, 커밋하는 요약과 fixture에는 우리 워크로드의 PID만 남긴다.
- 공개 레포다. 내부 IP, 호스트명, 회사 메일, 회사 코드·데이터를 커밋하지 않는다. 벤치마크는 합성 워크로드만 쓴다.
- sudo가 필요한 단계는 `[sudo]`로 표시하고 사용자가 직접 실행한다.

## Review Focus

spec이 암시하지만 놓치기 쉬운 실패 조건이다. 각 줄의 테스트는 괄호 안 Task에 들어 있다.

1. NVML/DCGM 필드가 `NOT_SUPPORTED`이거나 `N/A`를 돌려준다 → 0이 아니라 `N/A`로 보인다. (Task 9, 12, 13, 15)
2. `dcgmi`·`nsys`가 없거나 host engine이 꺼져 있다 → 크래시 없이 이유를 보여주고 NVML만으로 Live가 돈다. (Task 11, 15)
3. 프로세스 목록 조회와 상세 조회 사이에 프로세스가 사라진다 → 그 PID만 건너뛴다. (Task 12)
4. 캡처에 이벤트가 0개이거나 관찰 구간 길이가 0이다(MPS 환경 등) → 지표는 `None`이고 0으로 나누지 않는다. (Task 19)
5. 벤치마크 대상 GPU에 남의 프로세스나 남의 MPS 데몬이 있다 → 실행을 거부한다. (Task 23)
